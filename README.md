# ArchComposer

> 面向**讲解创作者**的建筑三维可视化解说编创工具。
> 核心主张：**视觉意图（Visual Intent）与视觉实现（Visual Realization）分离**——
> 创作者表达「我想强调什么」，系统负责「怎么拍」；换了讲解对象之后，
> 意图原样保留，构图自动重新求解。

计算机图形学课程项目 · 小组「勇闯天涯」（周昱醒 / 周佳俊 / 曾子睿）· 指导老师 周杰辉

## 快速开始

**前置条件**：Node.js ≥ 22.12（Vite 8 与 Vitest 5 的要求；实测 v22.23.5 可跑）。

```bash
cd archcomposer
npm install          # 或 npm ci（package-lock.json 已提交，装得更快更确定）
npm run dev          # 启动开发服务器，打开 http://localhost:5173
```

首次 `npm install` 会下载 three 与 vite，**耗时几分钟**；装完之后 `npm run dev`
启动约 3 秒。终端会打印 `VITE v8.3.4 ready in …ms` 与 `➜ Local: http://localhost:5173/`，
以及一行 LLM 代理的状态（见下）。

想验证**构建产物**而不是开发服务器：

```bash
npm run build        # 类型检查 + 生产构建，输出到 dist/
npm run preview      # 用静态服务器托管 dist/，打开 http://localhost:4173
```

> ⚠️ **不要用 `file://` 双击 `dist/index.html`。** 模型（`models/demohall.geometry.json`）
> 与示例分镜是用 `fetch()` 载入的，`file://` 协议下 fetch 会被 CORS 策略拦掉，页面会是空白。
> 必须经由一个静态服务器——`npm run dev`、`npm run preview`，或任意一个 http 服务器都行。

### 大语言模型（可选）

生成端默认就能用：**没有配置任何 API key 时走离线知识表**，功能完整、结果确定。
想接真实大模型，给 `npm run dev` 一个环境变量即可：

```bash
DEEPSEEK_API_KEY=sk-... npm run dev
```

启动横幅会相应地打印：

```
➜  LLM 代理：/api/llm → 已配置 API key（服务端环境变量）
➜  LLM 代理：/api/llm → 未配置 API key，前端将回退到离线生成（设置 DEEPSEEK_API_KEY 可启用大模型）
```

**key 不进浏览器。** 前端只发同源的 `/api/llm` 请求，由 dev server 的中间件
（`scripts/llm-proxy.mjs`）带上环境变量里的 key 转发给上游厂商。因此 key 不出现在
前端代码、本地存储或 DevTools 的网络面板里，也不受 CORS 限制。

代理也可独立起进程（供 `npm run preview` 或纯静态部署用）：

```bash
npm run llm:proxy    # 默认 http://127.0.0.1:8787/api/llm，端口由 LLM_PROXY_PORT 指定
```

界面上的「模型」页签（`data-tab="model"`）有设置面板：端点、模型名、key、温度，
以及一个探活按钮。温度会被夹到 `[0, 1.5]`；坏 JSON 静默退回默认值；
**代码里不存在任何硬编码凭据**（有断言 `normalizeLlmSettings({}).apiKey === ''`）。

### 首屏之后：两条路径，任选一条

首屏会自动加载内置模型「单层三开间悬山厅堂」（86 个构件，程序化生成）。
默认停在 **创作** 页签，四个页签依次是 创作 / 分镜 / 构件 / 模型。

## 路径 A：从一句话生成一套分镜

这是本项目「生成端」的入口。在 **创作** 页签的生成区：

1. 在目标框里写一句话，例如「给第一次参观的游客做一个 3 分钟讲解，重点介绍整体结构、屋顶和斗拱」（「观众」与「时长」有单独的输入框，时长默认 3 分钟）；
2. 点「生成讲解草稿」——出一份**草稿**，不是直接写进分镜；
3. 看草稿：标题、来源（`离线知识表` 或 `llm:deepseek-chat`）、每一步的目标与意图、时长、运镜，以及底部的 notes 与 warnings；
4. 点「采纳这 N 步」——**追加**到分镜末尾（不会覆盖你已有的步骤）；
5. 切到 **分镜** 页签，看到 `3 步 · 已求解 3 · 待重算 0 · 失败 0`；
   底部的播放条一直在（不属于任何页签），点「▶ 播放」听一遍，旁白与时钟会跟着走。

勾上「用大模型」会走真实模型。**它失败时的行为是设计过的，不是兜底了事**：

| 情形 | 行为 |
|---|---|
| 网络失败 / 没配 key | **回退到离线知识表**，并在 notes 里说明原因（实测文本含「大语言模型不可用」）。宁可给次优但可用的结果，也不给空白面板 |
| 模型返回了编造的构件 ID | 那一步被**丢弃**并计数，notes 里如实写明是哪个不存在的构件 |
| 模型**全部**编造 | **不回退**，显式报「无可用结果」。这和上一条性质不同：那是「没答上来」，这是「答非所问」，后者需要你知道 |
| 模型名留空 | 退回 `deepseek-chat` |

有一条硬约束：**幽灵步骤绝不进分镜**。一条指向不存在构件的步骤会以 `solve: 'failed'`
的形式留在分镜里，你看到的是一个红点而不知道原因——不如根本不让它进来，然后明确告诉你跳过了几条。

### 用一句话改：自然语言编辑指令

生成之后（或任何时候），在创作页签的「用一句话改」里写：

```
把斗拱放到第二步介绍 / 不要隐藏柱子 / 这一步环绕一周
```

点「解析这条指令」先出**预览**：每条识别出的指令列出类型、置信度百分比，以及**为什么这么判定**。
实测「这一步环绕一周」解析为「设置运镜 / 置信度 86%」。没能解析的片段会单独列出来，
不会被悄悄丢掉。确认无误再点「执行这 N 条」，结果逐条回报（如「✓ 第 3 步已设置环绕 360°」）。

支持 12 种指令：调整位置 / 删除步骤 / 复制步骤 / 设置视觉意图 / 改写旁白 / 调整时长 /
设置运镜 / 隐藏构件 / 保留构件 / 高亮构件 / 换目标构件 / 重算机位。

几个容易被做错的地方，都有针对性测试：**否定语气**（「不要把柱子隐藏掉」执行后该步
`effects.hidden` 长度为 0）、**目标是构件而非文字**（「把屋顶放到第一步」落到的是屋顶的
**构件 ID**，不是把标题文字改掉）、**越界删除不执行也不崩**、**一次说三件事时部分失败不影响其余**。

### 用一句话说问题：反馈驱动的局部调整

在「反馈」框里写你看到的问题，例如「这个视角看不清屋顶」。系统归因到 **观察视点**
层面，给出一条可执行建议；点「按这个调一下」，即按原意图重新求解该步骤的机位。
「柱子应该一直保留」则归因到 **效果** 层面。

**内容类反馈会被明确拒绝。** 输入「这一段讲得太复杂了」时归因结果是 `content`，
建议列表为空，旁白一字不改：

> 这类问题系统不替你改：讲什么由你决定，没有可以自动执行的动作。建议直接改那一步的旁白。

这是刻意划的边界。工具能算「这个机位被柱子挡住了」，算不了「这一段讲得好不好」。
把不能算的东西假装能算，是这类工具最容易走偏的地方。

## 路径 B：手工从零搭一套分镜

不生成也行。左侧构件列表选一个构件，右侧分镜面板跟上这五步：

1. 左侧构件列表选一个构件（例如「东侧柱」）；
2. 点「＋ 用选中构件新建步骤」；
3. 在步骤行里用下拉框选一个意图类型（或先录一段示范，让系统推断）；
4. 点「▷ 按意图求解机位」——得到机位，保真度与逐条约束的满足度会显示出来；
5. 点「⇄ 换目标并重解」——**换成同类构件的另一个，意图一个字段都没变，机位自动重解**。

第 5 步就是本项目的核心。想看得更清楚：记下第 4 步解出来的机位，
执行第 5 步后对比——相机换了位置，但「怎么讲」这件事（意图）原封不动。

### 360° 环绕运镜

步骤行上还有一个运镜下拉框，预设「全景环绕一周 · 360°」「环绕半周 · 180°」
「向右环绕 90°」「反向环绕半周 · -180°」。也可以用路径 A 里那句话设置。

运镜只描述**相对起始机位做什么运动**，不描述绝对轨迹——`camera` 仍然是这一步的锚点
（也就是重定向时被重解的那个量），运镜只是在锚点上叠加的相对运动。因此**重定向与运镜
不冲突**：换了目标之后 `camera` 重解，环绕仍然是「绕新目标转一圈」。

还有一条不变量：**设运镜之后 `solve` 仍然是 `solved`**，不会被标成 `stale`。
运镜不改变机位，也就不该让已求出的机位作废。走查里专门核对了这一点。

### 这五步是被机器验证过的

路径 B 的**语义**已被 `npm run walkthrough` 在真实 86 构件模型上自动走查过
（见「验证链」第 ⑦ 步），所以第 1~5 步一定会得出正确结果。

它**不能**替代浏览器里的人工走查：DOM 事件绑定、store 订阅的渲染时机、WebGL 上下文创建
都测不到。走查覆盖不到的是**界面本身**——按钮有没有接上、面板有没有刷新。
那部分已经由一次真实浏览器走查补上了（见「验证链」里的「浏览器内人工走查」）。

| 命令 | 作用 |
|---|---|
| `npm run dev` | 开发服务器（默认 http://localhost:5173），含 `/api/llm` 代理 |

| `npm run test` / `test:watch` | 单元测试 |
| `npm run llm:proxy` | 单独起 LLM 代理进程（默认端口 8787），供 preview 或静态部署用 |

| `npm run gen:example` | 重新生成内置示例分镜 |
| `npm run demo:redirect` | **端到端演示**：在真实 86 构件模型上跑六组重定向，打印保真度表格 |
| `npm run walkthrough` | **文档走查**：把路径 B 的五步在真实模型上跑一遍并断言（防止 README 悄悄过期） |
| `npm run smoke:generate` | 生成器自检：知识表完整性、离线生成、确定性、LLM 输出的校验与两条降级路径、提示词 |

| `npm run smoke:naming` / `smoke:model` | 命名规范 / 生成器的冒烟断言 |

**注意 `npm run verify` 要跑几分钟**：八步里含一次完整模型再生成与 303 项测试。
只想快速确认代码没坏时，`npm run check`（类型，约 10 秒）或 `npm run test` 就够。

## 验证链

`npm run verify` 依次执行八步，任一步失败即中止：

| 步骤 | 命令 | 检查什么 |
|---|---|---|
| ① 类型 | `tsc --noEmit` | 类型正确性；`erasableSyntaxOnly` 禁用 `enum`；无未使用变量 |
| ② 分层 | `check-layering.ts` | **28 个领域层文件零越界引用**（L3 不许碰 three，也不许反向依赖上层） |
| ③ 生成 | `gen:model` | 重新生成模型——确定性意味着这一步应当**无差异** |
| ④ 交付物 | `verify-output.ts` | 86 构件、**三链一致**（命名链 / 几何链 / 语义链）、零警告；示例分镜与模型一致且可复现 |
| ⑤ 冒烟 | `smoke:naming` + `smoke:model` | 37 + 38 项手写断言 |
| ⑥ 生成器自检 | `smoke:generate` | 18 项：知识表、离线生成、确定性、LLM 输出校验、两条降级路径、提示词 |
| ⑦ 文档走查 | `walkthrough` | 路径 B 的五步在真实模型上跑通（含「意图逐字段未变」的断言） |
| ⑧ 测试 | `vitest run` | **303 项单元测试**（11 个文件） |

当前状态：**八步全绿**。构建产物 777 kB / 208 kB gzip（一条 chunk 体积警告，
已把阈值调到 900 以匹配 three 的实际体积）。

## 目录结构

```
archcomposer/
├─ src/
│  ├─ core/            L1 基础设施：向量/四元数/投影、ID、Store、稳定序列化（零依赖）
│  ├─ runtime/         L2 运行时：**唯一碰 three 的地方**；几何装配、拾取、特效、示范录制
│  ├─ domain/          L3 领域：命名与语义、意图谓词、求解器、保真度、分镜完整性、
│  │                   生成器（generator/：知识表 + LLM 生成器 + 规则生成器）、
│  │                   语言（language/：指令解析 + 反馈归因）、运镜（motion/）（**不 import three**）
│  ├─ app/             L4 应用：命令层（唯一写入口）、Store 装配、播放、存取、
│  │                   LLM 客户端与设置（llm/）、生成编排（generate/）
│  ├─ ui/              L5 界面：面板（创作/分镜/构件/模型/设置）、时间轴、意图对话框
│  └─ __tests__/       303 项测试（11 个文件）
├─ scripts/            生成器、分层守卫、交付物自检、端到端演示、文档走查、
│                      生成器自检、LLM 代理（llm-proxy.mjs）
└─ public/
   ├─ models/          demohall.geometry.json + demohall.semantics.json（程序化生成，86 构件）
   └─ examples/        入口厅堂讲解.storyboard.json（内置示例分镜）
```

**依赖方向是单向的**：`L5 → L4 → L3 → L2 → L1`。这条规则不是靠自觉，而是由
`scripts/check-layering.ts` 在每次 `npm run verify` 时强制检查。

**为什么 L3 不许 import three**：求解器、保真度、意图谓词必须能在 Node 下跑。
否则论文的批量评估就得启动浏览器，而且算法测试会依赖 WebGL 上下文。
代价是 L3 手里只有 AABB 没有三角形——这个取舍的记录见任务三文档 §10.4 的 L-3。

顺带说：**生成、解析、归因这三件事全部落在 L3**，因为它们都是纯计算。
副作用（网络请求）在 L4，渲染在 L2，界面措辞在 L5。分层守卫因此把新增代码也一并管住了。

## 核心概念速查

**视觉意图是一等数据。** 一个分镜步骤里，`target`（讲什么）与 `intent`（怎么讲）是分开的两个字段：

```json
{
  "target":  { "form": "single", "component": { "id": "demohall@1/column_e__01", ... } },
  "intent":  { "kind": "EMPHASIZE", "predicates": [
                 { "measure": "screenCoverage", "subjects": [], "test": { "op": ">=", "value": 0.12 }, "weight": 1 },
                 { "measure": "unoccluded",    "subjects": [], "test": { "op": "==", "value": 1    }, "weight": 1 }
               ] },
  "camera":  { "position": [...], "quaternion": [...], "fovY": 0.785 },
  "motion":  { "kind": "orbit", "degrees": 360, "pivot": null },
  "solve":   "solved"
}
```

**`solve` 的四种状态**是本项目最关键的一个数据表示：

| 状态 | 含义 |
|---|---|
| `none` | 从未求解过 |
| `solved` | 当前 `camera` 与当前 `target` + `intent` 一致 |
| `stale` | **意图或目标被改过，机位是旧的**——这就是「意图可迁移」在数据层的体现 |
| `failed` | 求解失败，`camera` 保留旧值（**不允许静默写入劣质机位**） |

**`solve === 'stale'` 是本项目的核心不变量 I-ST-5**：改 `target` 或 `intent` 会让 `solve`
变成 `'stale'`，除非它原本是 `'none'`（从未求解的步骤不该被说成「待重算」）。
Navisworks 这类现有工具的视点**没有等价物**——它们的视点存的是「最终机位」，
所以改讲另一个构件就得重新摆一遍。本项目的视点存的是「意图」，因此可以自动重解。

**`camera` 与 `motion` 是两个量。** `camera` 描述这一步**停在哪**（静态位姿，也是重定向时
被重解的那个量）；`motion` 描述在锚点上**做什么相对运动**。因此改运镜不动 `solve`
（仍为 `solved`），换目标后 `motion` 也不用改——环绕枢轴默认取目标包围盒中心，换目标后
自动跟着换。

**谓词用统一形状，不需要 `switch (intent.kind)`**（NFR-7）：

```ts
{ measure: 'screenCoverage', subjects: ['demohall@1/column_e__01'], test: { op: '>=', value: 0.12 }, weight: 1 }
```

五类意图（`EMPHASIZE` / `REDUCE_OCCLUSION` / `KEEP_CONTEXT` / `REVEAL_RELATION` /
`SHOW_OVERVIEW`）共享这套形状，求解器按 `measure` 查表求值，不判别 `kind`。

**生成草稿与分镜是两个东西。** 生成产出的是 `GenerationDraft`（还没有 ID、没有求解），
作者确认后由命令层 `adoptDraft` 落成分镜步骤。中间态存在的理由很实际：模型会编造构件名，
而你是唯一知道「这栋建筑到底有没有垂花柱」的人。

**指令通道与反馈通道的结果分开存。** 两个通道各有自己的结果槽（`outcomes` 与
`feedbackOutcomes`）。分开的理由是界面上它们隔着一个输入框——混在一起的话，你点完反馈框
里的按钮，结果会出现在上方「用一句话改」那一段里，看着像没反应。

## 技术栈

| 层 | 选型 | 版本 | 为什么 |
|---|---|---|---|
| 语言 | TypeScript | `~6.0.2` | `erasableSyntaxOnly` 禁 `enum`（用 `const` 对象 + 联合类型），`noUnusedLocals` 强制 |
| 渲染 | Three.js | `^0.186.1` | 只出现在 L2 |
| 构建 | Vite | `^8.3.0` | `base: './'` 让产物可放在任意子路径下；**不能**用 `file://` 直接打开（模型靠 `fetch` 载入，会被 CORS 拦），预览用 `npm run preview` |
| 测试 | Vitest | `^5.1.1` | 默认环境 `node`；只有 `ui.test.ts` 用 `happy-dom` |
| 模型 | 程序化生成 | — | 不用外部资产，仓库自包含；86 构件、确定性 |
| 大模型 | DeepSeek（可选） | — | 只经服务端代理访问，key 不进浏览器；不配也能跑 |

**测试环境为什么默认 `node`**：这是「L3 不碰 three」这条架构约束的直接体现。
如果哪天有算法测试必须用 DOM 才能跑，那说明有渲染依赖漏进了领域层——
`check-layering.ts` 会先一步报出来。

**为什么是 `happy-dom` 而不是 `jsdom`**：本沙箱里 `jsdom` 的模块加载耗时约 95 秒，
超过了 Vitest 的 worker 启动超时（60 秒），测试跑不起来；`happy-dom` 约 40 秒，能跑通。
这个选择是**环境所迫而非偏好**，在有正常网络的开发机上两者都可以。

**为什么代理只允许 POST 与 GET（探活）**：上游地址由环境变量控制而不是由请求体控制。
否则这个代理就成了「任何人都能用我们的 key 打任意地址」的 SSRF 跳板。

## 已知限制

如实列出，不掩饰：

| 项 | 说明 |
|---|---|
| 可见性判断基于 AABB | 对薄壳构件可能漏判。取舍记录见任务三文档 §10.4 L-3。 |
| 兼容性校验用构件数粗判 | 抓不到「一个构件被换成另一个但数量不变」。见 L-1。 |
| E1 用例人工挑选 | 见上文的警告。正式的 E1 需要穷举替换的批量评估。 |
| 没有做过方法对比实验 | 开题报告承诺了这项实验（对比「意图式重定向」与「直接摆机位」），仓库里目前没有对应工装。 |
| 没有做过创作者用户研究（E3 / NFR-1） | 需要招募到「建筑讲解创作者」这一目标人群，本课程周期内没有条件。`docs/01` §7.3 已将它定位为补充证据，主结论仍以 E1 / E2 为准。 |
| 内容类反馈不做自动处理 | 这是**设计边界**而非缺口。理由见上文「反馈驱动的局部调整」。 |
| 生成质量未做量化评估 | `smoke:generate` 保证的是格式合法、构件引用有效、确定性；「这套讲解讲得好不好」没有指标。 |
| Word 版本 | **不做**（用户明确指示）。全部交付物为 Markdown。 |

**早先那条「没有做过浏览器内人工走查」的缺口已经补上了**——见上文
「浏览器内人工走查（已补）」。当时它是任务四唯一的验收缺口；现在真正剩下的缺口是
上表里的**方法对比实验**、**创作者用户研究**与**生成质量评估**。

## 项目内发现并修正的真实缺陷

这些是**只有在真实 86 构件模型上跑真实用例才会暴露**的问题，已全部修正并写进文档：

1. **求解器成功时丢弃冲突清单**（违反「不许静默降级」）。注释写「不管成败都如实汇报」，
   实现却是 `const conflicts = ok ? [] : winner.conflicts`。后果：一条**物理上不可能满足**的
   约束会被其它约束的高分抬过接受阈值，判为「成功」而系统一声不吭。
   修正：加**最差约束惩罚** `overall = mean - 0.5 × (1 - worst)`，并先对每条谓词的分数开平方。
2. **AABB 邻接被误判成遮挡**。柱础（y 0~0.16）包含柱子底角（y=0），屋面包含柱顶角（y=4.0），
   于是「从相机到柱顶」的射线一出相机就撞在柱础上——六组重定向用例**保真度全部 0%**。
   修正：采样点落在对方包围盒内（1e-3 容差）时视为「贴着的邻居」。9/27 → 27/27 条射线畅通。
3. **采样最小距离过大**。采样距离以构件**最长边**为基准，柱子高 4.0 m 而横向只有 0.36 m，
   最小因子 2.6 意味着相机至少退到 10.4 m，柱子只占画面 **0.3%**，
   `EMPHASIZE` 的 12% 占比约束**永远不可能被满足**——「换一根柱子」这个最基本的用例直接不可用。
   修正：距离因子向下延伸到 `1.1`。
4. **`-0` 破坏存盘往返契约**。`quatLookAt` 内部用叉积，输出常含 `-0`；
   而 `JSON.stringify(-0)` 输出 `"0"`，导致「存盘再读回」的位姿与内存里的**不严格相等**。
   修正：`canonicalizePose()` 在数据离开 L3 前把所有 `-0` 规范成 `0`。
5. **「换同类构件」会把当前目标列为候选**。用户点了按钮却什么都没变，观感上就是功能坏了。
   修正：候选列表排除自身。
6. **失败区的候选 chip，点哪一个都换到排序第一的那个**。chip 只把自己的
   `step.id` 传出去，命令层于是按排序推荐挑了第一个——界面标签写着「西侧柱」，
   实际换成了「东侧柱」。**每个单元单独看都「对」，错在它们之间的接线**：
   chip 知道自己代表哪一个构件，却没把这个信息传下去。修正：
   `onRedirectStep(id, candidateId?)` 增加第二个参数。
   已做**负向验证**：退回缺陷版，新加的 ui 测试确实失败（1 failed / 23 passed）。
7. **打开页面没有模型**。根因在 `src/runtime/scene/viewport.ts` 的 `frame()`：模型组被构建、
   注册、可拾取、可加特效，**但从未 `scene.add` 进场景**。注册/拾取/特效三层都只持有对象引用，
   谁都不负责挂进 scene；而渲染只认 scene 子树，所以界面显示「86 个构件」而画面空无一物。
   证据：修复前 `renderer.info.render.calls === 2`（只有两盏灯），修复后 **88**（2506 三角面）。
   修正 = `Viewport` 加 `framedRoot` 字段 + `frame()` 开头三行。
8. **反馈区的执行结果渲染到了指令区**。`onApplyDiagnosis` 把结果写进 `language.outcomes`，
   而界面上 `outcomes` 只渲染在「用一句话改」那个区块，反馈区块拿不到它。你点完反馈框里的
   按钮，结果出现在隔着两段的面板上方，看着像没反应。修正：`LanguageState` 增加独立结果槽
   `feedbackOutcomes`，反馈区渲染它。
9. **采纳草稿时的跳过提示报在远处**。同上性质：`onAdoptDraft` 把「有几条被跳过」写进了
   指令区。修正：改写到 generation store 的 `error`，渲染在**草稿原来的位置**——刚点完
   「采纳」的目光就在那里。

**第 1 条与第 2、3 条有因果关系**：正是「失败必须如实报告」这条设计决策，让第 2 条这个更根本的
bug 现了形——如果求解器按缺陷版的逻辑运行，那六组用例会「静默成功」，AABB 邻接的误判就被掩盖了。

**第 6、7、8、9 条是同一类问题**：每个单元单独看都「对」，错在它们之间的**接线**。
chip 知道自己是哪个构件、模型组知道自己的几何、结果槽知道自己存了什么——但信息没有传下去。
`check-layering.ts` 抓不到这类错，类型检查也抓不到（类型全对），**只有真的在浏览器里点一遍
才会暴露**。第 6 条与第 8 条都补了针对性的测试。

另有一个属于**验证工具自身**的缺陷（第 10 个）：走查脚本的辅助函数 `text()` 收的是 ID，
而调用点传的是 `.draft-title` 这类 CSS 选择器，于是走查日志里这些字段全是 `null`。
改成 `document.querySelector` 后全部有值。它不属于产品缺陷，但值得记一笔：
**验证脚本本身也需要被验证**——第一版走查打印出一屏 `null`，不细看会以为是功能没生效。
